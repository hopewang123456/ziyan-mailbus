## 附：灵霄 auto-ack & chat -q 超时治本思路

### 问题一：灵霄(Cline) auto-ack 不执行

**现象：** Cline hub-daemon 常驻后台，收到 mailbus CLI 推送后自动回复"完成回执"
（state=done），但实际代码没改、任务没执行。

**已验证的突破方法（2026-06-04 实战成功）：**
1. 推送消息中嵌入具体 shell 命令，如 sed + grep
2. 要求 agent 执行命令并返回 stdout
3. 命令的 stdout 可验证，auto-ack 无法伪造
4. 成功验证后，再正常派发后续任务

**治本思路：**
- mailbus 推送时消息体改为两步结构：①一条可验证的 shell 命令 ②后面的任务描述
- agent 必须先执行命令并返回结果，mailbus 确认 stdout 符合预期后才认为"已受理"
- 如果 agent 只回了 ACK 但没有命令产出，mailbus 标记为"未受理"重新推送或升级

### 问题二：chat -q 超时（Hermes/灵验/灵鉴）

**现象：** 推送消息太大（完整方案文档）→ chat -q 进程在模型调用阶段超时退出 →
消息被 auto-ack 标记为 done → 实际没人处理过

**已验证的缓解方法：**
1. 将 system context 从 300+ 行精简到 7 行核心信息
2. 只推关键指令，不附带完整方案文档

**治本思路：**
- mailbus 推送不依赖 chat -q 返回结果
- 改为：推送 → 检查目标 inbox 是否有 ack 文件 → 有则确认送达
- 任务执行结果通过灵巡巡检或定时扫描任务链来确认
- 不再等待 chat -q 进程返回，避免超时导致的"伪 done"状态


### 新增：消息大小限制

**问题：** 派工消息没有大小上限，导致 agent（Cline/OpenCode/Hermes chat -q）因消息太长
被 SIGKILL 或超时退出。

**方案：** mailbus 在推送前自动检查消息体大小：

| 角色 | 最大消息长度 | 超限处理 |
|------|-------------|---------|
| 开发工程师 | 500 字 | 拒绝推送，提示"请拆分为多个任务" |
| 审查官 | 1000 字 | 同上 |
| 调度员 | 800 字 | 同上 |
| 其他 | 1000 字 | 同上 |

**实现：** pusher.py 在 `_push()` 中检查 len(msg_content) > 500 时拒绝并打印告警。
