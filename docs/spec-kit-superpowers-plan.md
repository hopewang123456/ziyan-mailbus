# Spec Kit + Superpowers 引入方案

## 方案定位

两个工具互补，分阶段引入，不推倒现有架构。

### 核心原则
- **mailbus 不动** — 消息总线保持中立，不入侵 Agent 框架
- **Superpowers 做编排层** — 叠加在 mailbus 之上，声明式工作流
- **Spec Kit 做规范层** — 统一文档格式，辅助灵鉴审查

---

## Phase 1: Superpowers 试点（2天）

### 选哪条流程试点
**选择：灵鉴审查 → 灵验测试 流转**

理由：
1. 这是当前最成熟的流程（已经跑通了）
2. 问题最清晰（审查完要人工通知灵验）
3. 风险最低（不影响现有功能）

### 具体步骤

```
当前: 大力/灵霄写代码 → 灵鉴审 → (人工) → 灵验测
目标: 大力/灵霄写代码 → 灵鉴审 → 自动通知灵验 → 灵验测
```

1. 装 Superpowers CLI: `npm install -g superpowers`
2. 定义第一个工作流 YAML（审查→测试流转）
3. 接入 mailbus（审查完成 → Superpowers 触发 → 通知灵验）
4. 验证跑通

### 与 mailbus 的集成方式

```
mailbus scan 检测到审查完成
  → 触发 Superpowers workflow
  → workflow 执行: 更新状态 + 推消息给灵验
  → 灵验 ACK → workflow 标记完成
```

## Phase 2: Superpowers 推广（2天）

- 小七调度工作流（任务派发→执行→超时→升级）
- XSS 修复全链路（修复→审查→测试→上线审批）
- 告警处理流程（告警→派发→处理→闭环）

---

## Phase 3: Spec Kit（1天）

### 选哪条规范试点
**选择：代码审查规范**

理由：
1. 灵鉴已经在做审查，有不统一的痛点
2. 审查结果格式一致化后，可以自动化统计
3. 跟 Superpowers 的工作流可以联动

### 具体步骤
1. 装 Spec Kit CLI
2. 定义审查报告模板（YAML/JSON 结构）
3. 灵鉴出审查报告时用模板
4. 验证自动校验

| 风险 | 缓解 |
|------|------|

| 当前阻塞项（灵霄离线等） | 已修复，可以推进 |
